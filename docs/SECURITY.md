## Edge proxy and TLS

- **Only Caddy is reachable from the LAN**, on port 443. Inside its container it listens on 8443 as a non-root user (uid 10001) and needs no Linux capabilities (`cap_drop: [ALL]`, `no-new-privileges`, read-only root filesystem). The image is official Caddy plus the deSEC DNS plugin, base images pinned by digest; the file capability that `xcaddy` adds is stripped.
- **Plain HTTP is not served.** Port 80 is neither published nor listened on; HTTP/3 is off because UDP is not published.
- **HSTS** is sent on every response (`COMMONS_HSTS_MAX_AGE`, default one year, the test stack uses 300 s).
- **`/internal` is blocked at the proxy** (404 for all case and encoding variants, tested by `scripts/check_caddy.sh`). The bot reaches the app's internal API over the Docker network only. The app must still authenticate those requests with its service token; the proxy block is defence in depth. That includes the bot's event stream (`GET /internal/events`): it carries the feed lines the community room shows anyway, plus reminders to return things, each addressed to one member (`to`), which the bot sends to that member in a private chat and only to accounts on this homeserver, and each stream ends after `COMMONS_EVENTS_STREAM_SECONDS` (default 600) with a bounded per-client queue, so a stuck client can't hold memory.
- The Caddy admin API is off and the `Server` header is removed.

### Certificates: two modes (`COMMONS_TLS`)

| | `desec` (default for phones) | `internal` |
|---|---|---|
| Issuer | Let's Encrypt, via DNS-01 at deSEC | Caddy's own local CA |
| Members install anything? | No | Yes, the root certificate on every device |
| Element X | Works on iOS (tested 6 Nov 2026; Android still to test) | **Rejected** on iOS (tested 5 Nov 2026: `tls: unknown certificate`); browsers work |
| Internet needed | Only to issue/renew (every ~60 days, ~30 days of slack) | Never |
| Names | `commons.theoutpost.network`, `matrix.commons.theoutpost.network`, `auth.commons.theoutpost.network` | IPs or local names |

**Why `desec` works without exposing the box:** Let's Encrypt checks a TXT record that Caddy creates through the deSEC API, nothing on the internet ever connects to the box. The A records for the three COMMONS service hosts point to the box's **private LAN address**, which is meaningless outside the LAN (or VPN). Certificates are published in public Certificate Transparency logs, so these names are publicly visible which is expected and harmless.

**DNS delegation:** `theoutpost.network` (website, email) stays at GoDaddy. Only `commons.theoutpost.network` is delegated to deSEC (two NS records), so the token on the box can never touch the website or email.

### The deSEC token is a secret

- Stored in `secrets/desec_token` (mode 0600, git-ignored), mounted into Caddy as a Docker secret at `/run/secrets/desec_token` and read via `{file.…}`. It is never in the environment, the Caddyfile, logs or the process list (`scripts/update_dns.sh` passes it to curl on stdin).
- It can change DNS records for `commons.theoutpost.network` only. A leaked token could point these names elsewhere or obtain certificates for them, so: create it without "manage tokens" / "create/delete domains" permissions, revoke it in deSEC if the box is lost or compromised, and use a separate token for the real box.

### Internal mode: the root CA private key is sensitive

In `internal` mode, the local CA's private key (`/data/caddy/pki/authorities/local/root.key` in the `caddy-data` volume) can issue certificates that members' phones trust **for any website**. Whoever has it could intercept members' traffic.

- Never copy it out of the volume, commit it, or send it anywhere. Only `root.crt` (public) is ever distributed.
- The nightly backup includes the `caddy-data` volume, encrypted with the rest ([BACKUP.md](BACKUP.md)). The restored key must stay as secret as the original!
- If the key may have leaked, delete the volume so Caddy generates a new CA, ask members to remove the old certificate and install the new one, and record the incident!

### Known limitations and open points

- **Offline:** in `desec` mode HTTPS keeps working with the WAN down until the certificate expires (Caddy renews 30 days before expiry). Phones must still resolve the names: today they use public DNS, which needs internet. The real box needs a local DNS answer for these names (follow-up).
- **Routers or DNS resolvers with rebind protection** may refuse answers that point to private addresses; then names don't resolve on that network.
- **Docker secret permissions on Linux:** the secret file is bind-mounted with its host owner and mode; the Caddy user (uid 10001) must be able to read it on the box (e.g. owner or group 10001). Docker Desktop on macOS does not enforce this.
- Connecting by **IP address** (internal mode) requires `COMMONS_DEFAULT_SNI` to be set to that IP, because clients send no server name for bare IPs.

## Matrix homeserver

- **Synapse** v1.164.2 with **Matrix Authentication Service (MAS)** v1.28.0 and **PostgreSQL** 17, all pinned by digest, non-root, read-only, no capabilities, with memory limits (Synapse 1 GB, MAS 256 MB, PostgreSQL 512 MB). Data in the `synapse-data` and `postgres-data` volumes (back up encrypted). Continuwuity was used until 9 Nov 2026 and has been removed.
- **No direct internet access:** Synapse, MAS, PostgreSQL and the app sit only on the `internal: true` Docker network. Caddy has egress (for Let's Encrypt/deSEC). Synapse's only way out is the **egress proxy** (below). Stats reporting, URL previews and the matrix.org key server are switched off.
- **Closed server:** federation off (`federation_domain_whitelist: []`, and `/_matrix/federation/*`, `/_matrix/key/*` return 404 at Caddy), sign-up in MAS only with a single-use registration token (`deploy/synapse/mas-accounts.yaml`), no email and no password recovery. Admins create tokens as invites on the COMMONS admin page (below); the first admin's account is made with `mas-cli manage register-user`, whose password is typed into the MAS prompt, never passed on the command line by our scripts.
- **Discovery:** `https://commons.theoutpost.network/.well-known/matrix/client` points clients to `matrix.commons.theoutpost.network`. User IDs are `@name:commons.theoutpost.network`; this `server_name` is permanent.
- **Login** happens on MAS's own login page at `auth.<domain>` (OAuth); clients like Element never see the password.
- **Push notifications** go through the **egress proxy** (`deploy/egress`, tinyproxy, pinned): Synapse sends outgoing requests to it (`HTTPS_PROXY`; internal calls to MAS and PostgreSQL bypass it), and it only allows HTTPS (`CONNECT` to port 443) to host names in `deploy/egress/allowlist.txt`, currently `matrix.org` (Element's push gateway) and `opendata-download-metfcst.smhi.se` (weather, see below). Everything else is refused (tested: other hosts, lookalike names, other ports, plain HTTP). Element X is designed to request the `event_id_only` push format, so Element's gateway and Apple/Google should only see the event ID, room ID, unread count and device push key, **not message content or sender**. Checked on 16 Nov 2026 with `make check-pushers` (reads Synapse's `pushers` table, never the push keys): all 3 registered pushers (Element X on Android and iOS) use `event_id_only` and matrix.org; there are no Element Web pushers. Two layers: the format keeps the sender and room name out, and `push.include_content: false` makes Synapse leave out the message text even for a client that doesn't ask for `event_id_only`. Run `make check-pushers` after new members set up their phones; it exits 1 if an enabled pusher uses another format, and that member's client (and whether to accept it) gets written down here. The phone fetches the message from our server. This is a deliberate trade-off: without it no member gets notified. A fully local alternative exists only for Android (UnifiedPush with a self-hosted ntfy).
- **Element Web from app.element.io** loads the client code from Element's site (the browser then talks directly to our server). Chrome/Edge ask for "local network access" because our server has a private address. A self-hosted Element Web would avoid both (follow-up).

## Dashboard sign-in

- **One account per member, the Matrix account.** COMMONS stores no passwords; `member` holds the Matrix user id, roles live in `member_role`. Only accounts on our own homeserver are accepted.
- **Sign in with Matrix** is OAuth 2.0 (authorization code + PKCE, `state` bound to the browser with a short-lived cookie). COMMONS registers itself once with the homeserver and keeps the client id in `/data`.
- **Token scope:** COMMONS requests only the `openid` scope. The token has no Matrix API access and creates no device. COMMONS reads the username from MAS's `userinfo`, revokes the token, and checks at MAS (not at Synapse, which caches token checks) that it is dead.
- The token is never stored or logged, and sign-in fails if revocation can't be confirmed. (The app still has a `whoami` fallback for homeservers without `userinfo`, from the Continuwuity days.)

## Members, roles and guards

- **Default deny:** every route needs an explicit guard (`require_member`, `require_role(...)` or the internal service token). `tests/test_route_guards.py` walks all routes, included routers too, and fails on any route that has no guard and isn't on the short public list (`/`, `/health`, `/auth/login`, `/auth/callback`, `/join/{code}`).
- **Authorization matrix:** `tests/test_authz_matrix.py` lists every route with the status each caller must get (not signed in, member, board, admin, bot) and calls each route as each of them, with a valid CSRF token so only the permission check decides. Refused requests must change nothing (COMMONS rows and MAS calls are checked). The test fails if a route has no row, so every new feature has to state who may use it.
- **Admin pages** (`/admin/*`) check the admin role before anything else, so a member or board member gets 403 whatever they send. Every admin POST also needs the CSRF token.
- **Always an admin:** the last active admin can't lose the role or be deactivated. The check locks the admin rows (`SELECT … FOR UPDATE`), so two admins removing each other at the same moment can't leave COMMONS without one (tested with two concurrent transactions).
- **First admin:** `make bootstrap-admin` only works while there is no active admin. After that, admins are made on the admin page.
- **Deactivation** revokes all of the member's COMMONS sessions at once. Sign-in and chat commands are refused from then on. The member row stays, so history stays attributed.
- **Every account is a member:** an account on our homeserver becomes a member (role `member` only) on its first sign-in or chat message (`members.ensure_member`). This is safe because accounts can only be made with an admin's invite (MAS sign-up needs a registration token, federation is off). Accounts on other servers are refused. Extra roles only come from an admin. A deactivated member stays deactivated. Two first sign-ins at once can't create two members (unique Matrix id, tested).
- **Invites** are MAS registration tokens: `usage_limit` 1, expiry 24 h (`COMMONS_INVITE_HOURS`), created and revoked through the MAS admin API. The new person types their password into MAS only; COMMONS never sees it. The code has about 99 bits of randomness; COMMONS stores only its SHA-256 and MAS' token id, and shows the link to the admin once. `/join/<code>` is public but rate-limited, sends `Referrer-Policy: no-referrer` and `Cache-Control: no-store`, and answers 410 for unknown, used, expired or withdrawn codes. A valid code is put in the `commons_invite` cookie for `commons.<domain>` (so `auth.commons.<domain>` receives it; `Secure`, `SameSite=Lax`, 1 hour, not `HttpOnly` because MAS's page script reads it) and the browser goes straight to MAS's sign-up page. Our version of MAS's registration-token template (`deploy/mas/`, built on the pinned MAS image; the build fails if MAS's own template changes) fills the code in, deletes the cookie and submits once. The cookie holds only the single-use code that is in the link anyway; COMMONS also deletes it after sign-in. The modified template keeps MAS's AGPL licence header, and its source is in this repository. MAS checks the code again at sign-up, and Caddy rate-limits MAS's `/register` pages. The invite link carries the code, so anyone who sees the link before it is used can use it: send it to one person, withdraw it if it went astray.
- **Deactivation locks the chat account too:** the admin page locks the member's MAS account (MAS admin API) before it commits the deactivation; if MAS doesn't answer, nothing changes. Reactivation unlocks it. The CLI can't reach the admin API and prints the `mas-cli manage lock-user` command instead.
- **Deleting a member** is only possible while no other row in COMMONS refers to them: every table that records an action points at `member.id`, so PostgreSQL refuses the delete once they have done anything, and they must be deactivated instead (history stays attributed; this also stops an admin from removing someone's traces). Their own roles, sessions and sign-in history are removed with them. Never the last admin, never yourself. COMMONS checks first, then MAS deactivates the account with erase (sessions end, rooms left, Synapse erases profile and messages), then COMMONS commits; if MAS fails, nothing is deleted. Admins confirm on a separate page.
- **Only our homeserver:** the CLI accepts only Matrix IDs on our own server name.
- **Anyone can check the decision log:** every signed-in member can verify the chain (hashes, links, Ed25519 signatures) with a recount of every closed vote from the logged counts, download the whole log and the public keys, and check them offline with `scripts/verify_log.py`, which runs the same code (`app/chain_verify.py`, standard library plus `cryptography`, no database). The replay catches a forged outcome and invented or dropped voters even when the forger holds the signing key; it can't catch votes moved between options without changing the outcome, because ballots are secret. Anchors (`--anchor seq:hash`) catch a rewritten or truncated chain, also one re-signed with the box's key: COMMONS posts one to the community room after every closed vote and once a day (`app/anchors.py`), so members' phones hold copies an admin with root on the box can't take back. A daily `ledger.digest` seals each day's ledger entries (SHA-256 over their canonical JSON), so edited or added ledger rows show too.
- **Membership changes are in the decision log:** creating an invite, granting or revoking a role and deactivating a member each append a signed entry (`member.invited`, `role.granted`, `role.revoked`, `member.deactivated`) in the same transaction as the change, so a change without its entry (or the reverse) can't commit. The actor is the admin (`null` from the command line) and the payload names the member by id and Matrix id plus the channel (`web` or `cli`). Invite entries hold the invite id and expiry only, never the code, its hash or the admin's note. Refused and no-op changes write nothing. The `member` role that comes with a new account is not logged (its invite is). The CLI loads the same signing key as the app (it creates it on a fresh install, so `make bootstrap-admin` makes the first admin the first entry) and refuses to start a second key if the key file is missing.
- **Reading the log:** `/log` is open to every signed-in member, not only admins, because the log is how members check the admins. It lists votes opening, closing with their outcome, and being cancelled, newest first (50 per page) with their payload, hashes and signature, shows the public signing key, and verifies the whole chain on every load, including the entries it doesn't list (ballots without choices, role and configuration changes); a broken chain is shown as an alert naming the first bad entry. Read-only (GET, no state change); payload text is escaped like everything else. The log holds no secrets: invite codes, their hashes and admin notes are never written to it.
- **Secret ballots (votes):** `vote.cast` / `vote.changed` entries name the voter (turnout, reminders) but never the option, and no page or event shows another member's choice, not even to the board or admins; members see anonymous counts and their own vote. For `after_close` vote types (events) the counts appear only once the vote has closed. Limits, stated honestly: the `vote` table must link a member to an option so each member has exactly one changeable vote, so anyone with database access (a rogue admin on the box) can read ballots; with live counts, watching the count move right after someone's "voted on" entry can reveal a choice, and a vote with very few voters reveals itself. The log lets members check turnout and that the outcome follows from the logged counts and rules, but not recount individual ballots.
- **Not yet:** reactivating a member is not logged (there is no decision-log kind for it), and withdrawing an invite isn't either.
- **Database:** PostgreSQL. COMMONS has its own database and role; `CONNECT` on the `synapse` and `mas` databases is revoked from everyone but their owner, so COMMONS cannot read chat or account data directly. The password is the `database_password` secret.
- **Sessions:** random 32-byte token, only its SHA-256 stored, cookie `HttpOnly; Secure; SameSite=Lax`, 14 days idle expiry, rotated on sign-in, logout and "log out on all devices" with CSRF tokens. Deactivated members lose access immediately.
- **CSRF:** one token per session, derived from the session cookie (SHA-256, so no extra storage). Pages carry it in `<meta name="csrf-token">`, in `hx-headers` on `<body>` (htmx sends it as `X-CSRF-Token`) and in each form's `csrf_token` field. `app/security.py` checks every POST, PUT, PATCH and DELETE that carries a session cookie before any route runs, and answers 403 if the token is missing or wrong (constant-time compare). Only urlencoded forms (up to 1 MB) or the header can carry it. Requests without a session cookie act for no one and get the route's own 401. `/internal/*` is exempt: the bot uses a bearer token, never cookies. The route-level checks (`CsrfChecked`, `AdminCsrfChecked`) stay as a second line.
- **Security headers** on every response, including errors and static files: `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin` (a route may set a stricter one, as the join page does with `no-referrer`) and a `Permissions-Policy` that turns off camera, microphone, geolocation, payment, USB and ad-interest APIs. Caddy adds HSTS. Templates hold no inline styles, scripts or event handlers (a test enforces it). htmx is configured not to inject styles or evaluate JavaScript and keeps no page history in `localStorage`.
- **Vendored JavaScript:** htmx 2.0.11 and its SSE extension 2.2.4 live in `app/static/vendor/`, checked against the npm registry's integrity hashes when added and pinned by `SHA256SUMS` (a test fails on any change). Nothing is loaded from a CDN.
- **Rate limits:** the dashboard's sign-in routes allow 10 requests per minute per client IP. MAS has its own login limits; in addition Caddy (`caddy-ratelimit` plugin) limits POSTs to the MAS login pages and the Matrix login endpoints to 10 per minute (and 60 per hour for the Matrix endpoints) per client IP (`scripts/check_login_limit.sh`).
- **Known limitations:**
  - MAS shows its consent page on every sign-in; it doesn't remember approvals (MAS v1.28 always redirects a logged-in user to consent).
  - Its password login API reveals whether an account exists.
  - Logging out of COMMONS does not log the browser out of the Matrix login page.
  - On Docker Desktop (macOS) Caddy may see every client with the same IP, so the limit is shared there.

## Community settings and resources

- **community.yaml** is read once, on the first start, and checked with a strict schema (unknown keys are errors). It holds no secrets. After seeding the app doesn't read it again, so a later edit can't change a running box behind the admins' backs; changes go through the admin pages and the decision log.
- **Resource admin pages** (`/admin/resources*`) need the admin role and, for every change, the CSRF token; all are rows in `tests/test_authz_matrix.py`. Forms are validated server-side with length limits; every POST redirects, so a reload never submits twice.
- **No history is lost:** a resource is deleted only while nothing refers to it. Ledger entries point at it, so PostgreSQL then refuses the delete and the admin archives it instead (tested with a stand-in table).
- **Unambiguous chat words:** id, name and chat words of all resources are unique (case-insensitive) in code, and chat words also by the `resource_alias` primary key, so the bot can never pick the wrong resource.
- **Bookable page** (`/admin/bookable*`) works like the resource pages: admin role, CSRF token, server-side validation, a row per route in `tests/test_authz_matrix.py`. A thing with bookings can only be archived; PostgreSQL refuses the delete.
- **Usage history** (`/admin/resources/{id}/history` and `history.csv`, feature 4) is admin only, checked in the route (members and board get 403; rows in `tests/test_authz_matrix.py`); it only reads. The CSV holds member names and notes, so it is sent with `Cache-Control: no-store`, and text a member typed (name, note) that starts with `=`, `+`, `-`, `@`, a tab or a line break gets a leading `'`, so a spreadsheet shows it instead of running it as a formula (CSV injection). Numbers are never altered. The chart is inline SVG drawn from numbers on the server: no chart library, no script, nothing from outside.
- **Bookings:** members change and give back only their own bookings; an admin changing or cancelling someone else's is written to the decision log (`booking.changed_by_admin`, `booking.cancelled_by_admin`). A trigger keeps who booked what fixed and refuses deletes.
- **Calendar pages** (`/calendar*`) need a signed-in member; every change needs the CSRF token and goes through the booking service as that member, so the web can't do more than chat. Changing, giving back and cancelling someone else's booking is refused (403) unless an admin does it, which is logged. Each route has a row in `tests/test_authz_matrix.py`.
- **Phone-calendar link** (`/calendar/ics/<token>.ics`) is the one public route besides sign-in: calendar apps can't sign in, so a 256-bit random token in the address is the permission. Only its SHA-256 is stored; a filter on uvicorn's access log replaces it with `[token]` (Caddy keeps no access log); responses are `no-store`; requests are rate-limited per address; unknown, revoked and deactivated members' tokens all get the same 404. The feed holds only the member's own bookings. Anyone who gets the link can read those bookings until it is stopped, so the page says to treat it like a password and lets the member stop or replace it at any time.
- **Settings changes are signed:** every change to resources and bookable things writes a `config.changed` entry with the admin as actor and old/new values in the same transaction, so a rogue admin can't quietly reconfigure the box. A refused request writes nothing (tested).
- **Stylesheet and script:** `/static` is public, like any site's CSS and JS, and holds only `app.css`, `app.js` and `vendor/` (tested). `app.js` is first-party, served from the same origin under the `script-src 'self'` CSP, and only closes the account menu on a click outside or Escape and copies a one-time link (invite, phone calendar) to the clipboard when its Copy button is pressed; every page works without it, and the link stays selectable text. No CDN, no external fonts.

## Ledger

- **One write path:** every resource entry goes through `ledger.add_entry` / `edit_entry` / `correct_entry`, which check the member (active), the resource (active, right entry type), the amount (finite, >= 0, at most twice the capacity or 1,000,000) and the time (at most 30 days back, not in the future). Every entry stores `member_id` and `channel`.
- **History can't be rewritten:** a PostgreSQL trigger on `resource_entry` refuses every DELETE, every UPDATE after the 15-minute edit window, and any change of who logged it, for what, its type or its target. A check constraint ties `correction` rows to the entry they fix, and only a correction can be `void` (an undo); the trigger also refuses turning an undo back into something else. Corrections never change the original row. From chat, an entry is chosen only by a number the member wrote or as the sender's own last entry, never by the model alone. Resources and members with entries can't be deleted (foreign keys), only archived or deactivated.
- **Permissions:** any active member logs as themselves; only the author edits (15 minutes); the author or an admin corrects. The web form needs the CSRF token and redirects after the POST (`tests/test_authz_matrix.py` row `/ledger/entries`). Notes are limited to 140 characters and escaped on output.
- **Events** are delivered only after the database commit, never after a rollback; a failing subscriber is logged and doesn't affect the write.

## Weather forecast (SMHI)

- **Third documented runtime exception** (approved for the test phase, 9 Nov 2026). COMMONS works without it; members then get "no weather forecast right now".
- **What leaves the box:** one HTTPS request every 30 minutes to SMHI's open-data forecast API (`opendata-download-metfcst.smhi.se`, Sweden's public weather service, CC BY 4.0, no account or key). The request carries only the configured coordinates, rounded to 3 decimals (about 100 m; SMHI's grid is 2.5 km). It carries nothing about members: no cookies, no tokens, and it isn't triggered by member messages.
- **How:** the app is on the internal network only and has no direct internet access. It reaches SMHI through the `egress` proxy, whose allowlist has exactly two hosts. The answer is size-limited (2 MB) and validated value by value; implausible entries are dropped.
- **In chat:** the model only recognises a weather question (intent `weather`); code builds the reply from the last good forecast in memory and names SMHI as the source. If SMHI can't be reached, the last forecast is kept and the reply says how old it is.
- **Configuration:** `COMMONS_WEATHER_LATITUDE`, `COMMONS_WEATHER_LONGITUDE` and `COMMONS_WEATHER_PLACE` (in `docker-compose.yml`). Unset coordinates switch it off completely. Follow-up: move these into the community configuration (`community.yaml` / admin UI).

## Chat assistant, bot and local model

- **Three parts, internal network only.** `bot` (`bot/`, mautrix-python) relays messages, the COMMONS app (`app/assistant.py`) decides, and `llm` (llama.cpp `llama-server`, image pinned by digest) understands language. None publishes a port or has internet access. `bot` and `llm` run as uid 10001, read-only, with no capabilities and memory limits.
- **The bot is a relay.** It has no database access, no model access and no logic. It posts each message with the sender's Matrix id to `POST /internal/assistant`, using the `internal_api_token` service token (compared in constant time), and sends back the reply. Private messages from COMMONS (reminders to give a thing back, `bot/dm.py`) are written by the app; the bot only delivers them to the member's existing 1:1 room with the bot, never to the community room, or opens a new encrypted direct room. Caddy answers 404 for `/internal` on every public host.
- **The app acts as the sender.** It looks up the member by Matrix id (non-members and deactivated members get a refusal) and acts with that member's rights only.
- **Vote message intros:** the model may write one neutral opening sentence for a vote message. The vote question reaches it only in the user turn, and code refuses any line with a link, mention, number, result or recommendation. All facts in the message come from code.
- **The model proposes, code decides.** Every message goes to the model first; fixed phrasings (rules) answer only when the model server is down. The model must answer with one JSON object (llama.cpp enforces `INTENT_SCHEMA`): one of the allow-listed intents `set_display_name`, `show_profile`, `weather`, `log_entry`, `correct_entry`, `show_levels`, `show_history`, `show_votes`, `book`, `check_availability`, `my_bookings`, `list_bookables`, `return_item`, `cancel_booking`, `change_booking`, `help` or `chat`, plus `about` (`me` or `someone_else`). Code validates it and refuses anything off the list.
  - Tools only ever act on the sender, whatever the message says.
  - A request about someone else is refused, also when the model misses it but the text says "Adelia's name" or "his name".
  - **Logging from chat** (`app/chat_ledger.py`): the model only proposes words (resource, type, amount, unit, day, time, note); there is no field for a member or a resource id. Code resolves the resource by name or chat word, checks the unit and logs through the ledger as the sender, with all ledger checks. Because a small model fills in plausible values, a proposal is **grounded in the message**: an amount counts only if that number is in the text, a time only if that time is written, "yesterday" only if the word is there, the resource only if the message names it (its name, id or a chat word, or an amount in a unit no other resource uses, as in "it's at 2000l now"; otherwise code asks which resource), a note only if the member wrote those words, and a question is never logged (the live model once turned "how much water do we have?" into a reading of 1,000 l). Requests to log for someone else ("for Adelia", "as Nora", "on behalf of …") are refused. Unclear requests get a question back, never a guess. The system prompt lists the configured resources (names, units, chat words) and nothing about members. It also carries the community's guide from `community.yaml` (house rules, chores, waste, travel): text the community wrote, with no member data, length-checked at seeding; the model answers questions about the place from it as a plain `chat` reply and can't act on it.
  - **Levels and history** (`app/chat_levels.py`): the reply is written by code from the ledger; the model only names the resource and, for history, a count (capped at 20). Its own text is ignored, so it can't make up a level. A question the model mislabels as a log entry is answered, never logged.
  - **Bookings from chat** (`app/chat_booking.py`): the model only names the action, the thing (by name), a note and where to; no member, booking or thing id except a booking number the member wrote ("booking #12"), which is only ever one of the sender's own. Dates and times are never taken from the model: code reads them from the message. A note or destination the model proposes counts only if those words are in the message. Booking, changing, giving back and cancelling go through `app/calendar.py` as the sender, with every check the web has; someone else's booking can't be reached, and a request naming another member ("for Frida", "for @ana", "on behalf of …", "for him"), or for cancelling, changing or giving back another member's booking ("cancel Ana's workshop booking"), or with another member as the one doing it ("Ana is done with the saw", "Frida brought the car back"), is refused, so the sender's own booking isn't touched by mistake. Full-width and other look-alike letters are read as plain ones (NFKC) and zero-width characters are removed first, so a name can't slip past in disguise. **When the model had to guess, nothing is written before the member answers "yes"** to an echo of it: a thing the member didn't name in this message (only the model's reading of the chat says which), a thing other than the one the message names, a booking number the message doesn't contain, or a time taken from an earlier message. A request that names the thing itself is carried out at once, as the sender and with every check, and the reply says what was done; a give-back or cancel can't be undone in COMMONS, so the echo stays for every guess. Offers wait in RAM for 10 minutes per room and sender, and every check runs again on "yes".
  - The model's own words are sent back only for small talk.
  - Member messages go only into the user turn, never into the system prompt.
- **Display names:** Matrix is the source of truth, and COMMONS keeps a copy, refreshed at sign-in and on "who am I?". Names are cleaned (one line, 1–64 characters, no control or invisible characters, not starting with "@").
  - **How a change is made:** COMMONS has its own OAuth client at MAS (`scripts/commons_admin_client.py`, client-credentials grant, scope `urn:mas:admin`, tokens in memory only). With it, it opens a personal session that acts for that one member, with only the Matrix client-API scope and a 60-second lifetime. It sets the name as the member and revokes the session at once.
  - **No server-admin rights:** COMMONS never holds Synapse admin rights; MAS refuses `urn:synapse:admin:*` to client-credentials tokens anyway.
  - **Admin API is private:** the MAS admin API listens only on an internal port (8081) that Caddy doesn't proxy (`deploy/synapse/mas-admin-listener.yaml`).
  - **Failure and logging:** Matrix is changed first; if that fails, nothing changes. Changes are logged in `auth_event` (`display_name_changed`, channel `matrix`).
- **Model:** SmolLM3-3B (Q4_K_M). It is downloaded once with `make fetch-model` from a URL pinned to one Hugging Face commit and checked against `deploy/models.sha256`, then mounted read-only. llama-server runs with `--offline`, its web UI is off, and it needs the `llm_api_key` secret, which only the app holds.
- **Bot account:** `@commons` exists in MAS without a password, so nobody can sign in as it. It has a single compatibility token for the fixed device `COMMONSBOT` (`scripts/bot_token.sh`, secret `bot_access_token`). On start the bot checks that the token belongs to that user and device.
- **End-to-end encryption:** Element X only creates encrypted DMs, so the bot encrypts too (libolm via `python-olm`). The encryption keys (in `bot.db`, encrypted with the `bot_pickle_key` secret) and the cross-signing recovery key (file mode 0600) live in the `bot-data` volume. Back that volume up encrypted. If it is lost, the bot needs a new identity.
- **Who it answers:** only accounts on our homeserver. It joins rooms only when invited by one. It answers every message in a 1:1 chat, and in group rooms only when @-mentioned or addressed as "commons, …". It ignores messages from before it started, edits and non-text messages.
- **Limits:** 6 messages per minute per member and 2,000 characters per message. Small-talk replies are cut at 1,500 characters, and the model handles one request at a time.
- **Privacy:** COMMONS keeps no copy of conversations. With each message the bot passes the last 10 messages of that chat from Matrix (only the member's and COMMONS' own; other people in a group room are left out), validated by the app (at most 20, 4,000 characters each, roles `user`/`assistant` only), and they go to the local model as earlier turns, never into the system prompt. Only an open "yes/no?" offer is held in the app's RAM, for 10 minutes. Message text is never logged, and mautrix's debug logging, which includes request bodies, is off.
- **Known limitations:** the internal API trusts the sender id the bot passes; anyone holding the service token could act as any member, so the token is a high-value secret. Small talk is still a plain chat with the model.



During testing the server can be reached through **Tailscale**: the DNS names point to the server's Tailscale address (`100.x`), so devices need Tailscale switched on, at home and on the road. Traffic is end-to-end WireGuard-encrypted, but Tailscale Inc. runs the coordination service, which conflicts with "no cloud at runtime". It is a stand-in; the intended setup is a self-run VPN (WireGuard, or IKEv2 through a small rented server where the connection is behind CGNAT, as with Starlink).
